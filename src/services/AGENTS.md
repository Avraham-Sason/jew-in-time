# AGENTS.md

## Purpose

- Own non-React app logic and native-facing service wrappers.

## Ownership

- [ZmanimService.ts](ZmanimService.ts) owns kosher-zmanim calculations and caching, and the per-location candle-lighting minutes (`candleLightingMinutes()`, `isJerusalem()`). They live here, below every caller, so no service imports the mitzvah registry and no require cycle forms.
- [HebcalService.ts](HebcalService.ts) owns Hebrew calendar, holidays, Shabbat, chol hamoed, holy blocks, Daf Yomi, and Omer logic.
- [LocationService.ts](LocationService.ts) owns location access wrappers.
- [StorageService.ts](StorageService.ts) owns MMKV-backed storage helpers.
- [TaharahStorage.ts](TaharahStorage.ts) owns the encrypted MMKV instance behind [../stores/useTaharahStore.ts](../stores/useTaharahStore.ts), its key in the secure store, and `clearTaharahStorage()`.
- [biometricLock.ts](biometricLock.ts) owns the taharah biometric lock: `lockStatusFor()`, `biometricsAvailable()`, `authenticate()` (one shared prompt at a time, `isAuthenticating()`), and the module-level session (`isSessionUnlocked()`, `markUnlocked()`, `relock()`) used by [../components/TaharahLock.tsx](../components/TaharahLock.tsx) and [../app/taharah/_layout.tsx](../app/taharah/_layout.tsx). It never touches the native module on web. `expo-local-authentication` is a native dependency, so the lock ships with a build. Its suite is [__tests__/biometricLock.test.ts](__tests__/biometricLock.test.ts); the root mock [expo-local-authentication.js](../../__mocks__/expo-local-authentication.js) stands in for the module (`__set`, `__reset`).
- [NotificationScheduler.ts](NotificationScheduler.ts) owns native notification scheduling, rebuilds, categories, and background tasks, including the taharah reminders built from [../utils/taharah/tasks.ts](../utils/taharah/tasks.ts).
- [NotificationScheduler.web.ts](NotificationScheduler.web.ts) owns web shim parity for scheduler exports.
- [notificationResponseHandler.ts](notificationResponseHandler.ts) owns notification tap/action responses.
- [SiddurService.ts](SiddurService.ts) owns loading a nusach text asset from disk (fetch on web), cached per nusach and text.
- [CompletionService.ts](CompletionService.ts) and [AppResetService.ts](AppResetService.ts) own completion/reset service behavior.
- [deviceSettings.ts](deviceSettings.ts) owns OS-settings deep links (battery optimisation exemption).
- [appUpdates.ts](appUpdates.ts) owns the version label settings shows (`appVersionLabel()`, `<version>-<n>` with `n` from `EXPO_PUBLIC_UPDATE_NUMBER`, see [../../scripts/publish-update.js](../../scripts/publish-update.js)) and the update helpers: `downloadNewUpdate()` returns the id of the update it downloaded, or null in development, with updates disabled or when nothing newer exists; `reloadIntoUpdate()` (never throws) serves home's reload banner and the tap handler; `isUpdateApplied({ updateId, updateCreatedAt })`, true when the running update is that update or a newer one (`Updates.createdAt` against the announced creation time), serves the tap handler and the scheduler's stale-notice check. expo-updates is already in the shipped binary, so all of it reaches installs over OTA.
- Service tests live in [__tests__/](__tests__/).

## Local Contracts

- Keep [NotificationScheduler.ts](NotificationScheduler.ts) and [NotificationScheduler.web.ts](NotificationScheduler.web.ts) API-compatible.
- Preserve notification identifiers as `${mitzvahId}__${YYYY-MM-DD}__${reminderIndex}` unless all scheduler, response, and tests are updated together. A notification not tied to a mitzvah (the pre-block notice, `blockNotice:<YYYY-MM-DD>`, the check-in reminders, `checkin:<YYYY-MM-DD>:<n>` with `data.blockId`, and the update notice, `update:<update id>` with `data.updateId`) uses an id without `__` and a `data.kind`, so `parseId` and every mitzvah lookup ignore it, and it carries no category (the taharah bedika reminders are the one exception, below).
- Check-in reminders come from `checkInFor()` in [../utils/checkIn.ts](../utils/checkIn.ts), for every block in the horizon and the three days before it, and are never scheduled for a finished check-in or one with nothing left to mark. `cancelCheckIn()` clears them from the tray and withdraws the rest through `rebuild()`, so a rebuild already in flight, which read the old state, is re-run instead of re-adding them. `settleCheckIn(date)` does the same after any mark or skip that leaves the day's check-in with nothing to mark; both are mirrored in the web shim. `shouldSuppressForCompletion()` and `dismissCompletedPresentedNotifications()` treat a settled check-in — finished, or nothing left to mark — like a done mitzvah.
- `MARK_DONE` must stay aligned with [../../scripts/withMitzvahNotificationAction.js](../../scripts/withMitzvahNotificationAction.js).
- Taharah reminders exist only while `useUserStore.taharahEnabled`. `taharahCandidates()` maps each horizon day's `taharahTasksFor()` tasks to `data.kind = 'taharah'` notifications, `data.taharah = { task, day, onah? }` with `day` the Hebrew abs: `hefsek` at the task's end minus `hefsekLeadMin`; `bedikaMorning` at sunrise plus 30 minutes and `bedikaEvening` at its end minus `bedikaEveningLeadMin`, both skipped once marked; `tevilaPrep` at tzeit minus `tevilaPrepLeadMin` plus `tevila` at tzeit; `perisha` at the onah's start; `bedikaVeset` an hour before the onah ends, only when it is required (the onah beinonit is among its reasons); `expectOnset` at 10:00 on the location's clock; and, for a woman only, `postBlock` 15 minutes after a holy block that left a clean day's bedika slot unmarked. Ids carry no `__`: `taharah:<task>:<day>`, `taharah:<task>:<day>:<night|day>` for `perisha` and `bedikaVeset`, `taharah:postBlock:<YYYY-MM-DD>`, `taharah:preBlock:<YYYY-MM-DD>` (the merge below); a repeated id keeps the first.
- With `discreetNotifications` (the default) every taharah notification shows only the neutral `taharah.notify.discreet*` text; otherwise it reads `taharah.notify.title.<task>` / `body.<task>`, with the disputed line when the onah is in dispute.
- `beforeQuiet()` is the one rule for taharah triggers: a trigger strictly inside a holy block goes out ten minutes before the block's candle lighting instead, unless the task's own window (`TaharahDraft.end`) outlasts the block, when it waits for the block's end (a perisha night opening at motzaei Shabbat's shkia fires at tzeit); a trigger not after now is dropped. A `tevila` whose own trigger is inside a block is replaced by its `tevilaPrep` alone, worded by `tevilaPrepShabbat` and naming candle lighting; the reminder for the later night still fires at the block's end.
- Drafts that `beforeQuiet()` pulled ahead of a block are grouped by the block they were moved out of, `quietBlockAt(draft.trigger).days[0]`; unshifted and deferred drafts are scheduled one by one. Every group, a lone draft included (its own text would name a deadline inside the block), becomes ONE notification: `taharah:preBlock:<first day of the block>`, `data.taharah = { task: 'preBlock', day }` with `day` the Hebrew abs of the block's first day (`firstDayAbs()`, shared with `postBlock`), no category, at the shifted instant. Discreet it reads `discreetTitle` / `discreet.preBlock`; otherwise `title.preBlock` with the block's `checkin.in.*` phrase, and a body of each member's own non-discreet title in the order the originals were due, repeated titles once, plus `taharah.disputed` once if any member is disputed. The members' own bodies (`tevilaPrepShabbat` included) are dropped in the merge.
- Only `bedikaMorning` and `bedikaEvening` carry the `taharah_bedika` category, one `MARK_DONE` button titled `taharah.notify.markDone`; no other taharah reminder has a category, so a hefsek or an immersion is only ever entered in the app. `markDoneFromNotificationData()` handles that button before any mitzvah lookup, in the headless action task too, by recording a clean `bedika` event for the slot, unless the slot already has a result, and dismisses the notification.
- `taharahNotificationSettled(data)` replays `deriveCycle()` over the store's events at the moment of asking: a bedika is settled when its clean day has no such slot left or the slot has a result, a `hefsek` once the cycle is past the hefsek stage, a `tevila` / `tevilaPrep` once the stage is `tahor`, a `postBlock` once no clean day in that block lacks a slot, an `expectOnset` once the latest onset is on or after its day; `perisha`, `bedikaVeset` and `preBlock` never. `shouldSuppressForCompletion()` and `dismissCompletedPresentedNotifications()` use it.
- `initNotificationHandlers()` also rebuilds on a `useTaharahStore` change of events, settings, the discreet switch or any lead, while `taharahEnabled` is on, and on a change of `taharahEnabled` itself. `SCHEDULE_FORMAT` is 5.
- `notifyIfUpdateReady(now)` runs at the end of every `DAILY_REBUILD_TASK` run (a failed check is logged with `console.warn` and never fails the task): it downloads a newer update through `downloadNewUpdate()` and presents one notice per update id, remembered under `UPDATE_NOTIFIED_KEY` only after the notice is scheduled, and withdraws the previously remembered notice first, so the tray holds one update notice at most and a run skipped for a holy block (`isQuietAt()` once onboarded), a switched-off notifications setting or a denied permission (`hasNotificationPermission()`) retries next hour. Title `update.notice.title`, body `home.updateReady`, Android on the default channel, immediate trigger. A notice carries `data.updateId` and `data.updateCreatedAt`; one whose update, or a newer one, is already running (`isUpdateApplied()`) is stale: `shouldSuppressForCompletion()` hides it and `dismissCompletedPresentedNotifications()` clears it from the tray at the next launch. `SCHEDULE_FORMAT` is unchanged: the notice is presented, never left pending.
- A reminder gets the `mitzvah_reminder_text` category (`OPEN_TEXT` + `MARK_DONE`) exactly when `hasSiddurText()` is true for its window date and its trigger is not a holy block's opening edge (`opensQuietBlock()`); otherwise `mitzvah_reminder`. `OPEN_TEXT` opens the app to the reader and needs no native handling; the Android plugin only dismisses on `MARK_DONE`.
- Category button titles are translated, so a language change rebuilds; it is part of the user-store subscription.
- Raise `SCHEDULE_FORMAT` whenever the shape of a scheduled notification changes (category, actions, payload). A rebuild deletes the stamp before it touches the schedule and writes it back when done, and a foreground with a missing or stale stamp rebuilds once — so an update, or a rebuild cut short by a reload (a language switch reloads the app for RTL), is redone; otherwise reminders already scheduled by the previous bundle keep the old shape until the next day.
- `cancelForMitzvah(id, date)` must cancel all pending reminders for that mitzvah/date and dismiss the ones already in the tray; every done and skip path relies on it.
- Always pass `Location` to `HebcalService.isShabbat(date, location)` when halachic boundary behavior matters.
- Holy blocks: `holyBlockAt(instant)` returns the block whose [candle lighting, tzeit] span contains the instant, edges included; `isHolyDay(date)` and `holyBlockOn(date)` are day-granular, judging the location's calendar date of `date` by its daytime. A block merges every touching Shabbat / Yom Tov / Yom Kippur day. Per-day holiday flags are memoized per Hebrew day and `inIsrael`.
- `isShabbat` and `isYomTov` both derive from one internal `hebrewDaysAt(instant, loc)` primitive. Its civil day is the instant's date in the LOCATION's zone, the same day `ZmanimService` resolves, never the device's. A Hebrew day turns over at shkia, and between shkia and tzeit both candidate days are returned so an observance counts if either carries it. Do not reintroduce a Gregorian-day check for either.
- Use `getHebrewDateAt(instant, loc)` for "today" displays (it advances at shkia) and `getHebrewDate(date)` only for calendar grids, where each cell is a civil day.
- Avoid UTC date shortcuts for mitzvah logic.
- `Zmanim.chatzotLayla` is chatzot halayla (solar midnight) for the night FOLLOWING that day, so it falls on the next civil date. It is the correct end for night windows.
- Battery-optimisation exemption is the user's half of reliable delivery; route it through `openBatteryOptimizationSettings()` and never request `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, which Google Play restricts to a narrow set of app categories.
- Exact-alarm delivery depends on the Android manifest, not on any runtime call; see the root AGENTS.md notification section before touching `android.permissions` or the config plugins.
- `ZmanimService` resolves the calendar day in the LOCATION's zone (`setDate` with a zoned Luxon DateTime, cache keyed on that ISO date). Never hand it a bare `Date`.
- `initNotificationHandlers()` returns a teardown; the caller must run it on unmount, or store subscriptions stack up and one change fans out N rebuilds.
- `withLock()` coalesces on the trailing edge: a request arriving mid-run queues exactly one re-run. Never make it drop-on-conflict.
- Only `rebuildForNewDay()` stamps `LAST_REBUILD_KEY`; a settings-driven `rebuild()` must not, or it suppresses that night's recovery run.
- Scheduling is capped and ordered by trigger time (`IOS_MAX`/`PENDING_LIMIT`), every candidate carries `channelId` on the trigger, and a trigger outside its own window is dropped.
- Whether a reminder fires is `reminderFires()` from [../utils/skipRules.ts](../utils/skipRules.ts): ahead, inside its own window, and not strictly inside a holy block. The scheduler and the mitzvah screen's next-reminder preview both use it. The horizon steps by the location's calendar dates through any block that is reached or starts the next day, to the first weekday after it; each step is the device-local midnight of that date, with zmanim at the location's noon, the mapping every day-level surface uses.
- [notificationResponseHandler.ts](notificationResponseHandler.ts) opens nothing while the app is quiet (onboarded and `isQuietAt()` now), drops a buffered cold-start tap then too, routes the pre-block notice to home, a check-in reminder to `/checkin` and a taharah reminder to `/taharah`, and reloads into the update for an update notice through `reloadIntoUpdate()`, or opens home when that update, or a newer one, is already running. `MARK_DONE` is never blocked.
- `AppResetService` wraps its work in `setSchedulingSuspended(true)` so resetting the stores cannot re-arm a schedule from the restored defaults. It resets `useTaharahStore` with the other stores and, after the main MMKV wipe, calls `clearTaharahStorage()`.
- The taharah instance (`jew-in-time-taharah`) is encrypted with a 16-character key held in `expo-secure-store` under `taharah-mmkv-key`, read synchronously at module load and made on first use from `expo-crypto` random bytes. The key is always stored with `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`: it never travels in a backup or device transfer, yet the nightly rebuild and a lock-screen mark-done still read it on a locked phone. A key made just now clears the file it opens, since it cannot open anything older.
- When no key is available (web, or a keychain that cannot be read, such as a launch while the device is locked) the module opens a different, unencrypted file (`jew-in-time-taharah-unencrypted`). It must never open the encrypted file without its key: that decodes ciphertext as data and corrupts it.
- `clearTaharahStorage()` wipes the data and replaces the key in the secure store and in the running instance (`recrypt`). Deleting the key instead would leave this process writing under a key the next launch no longer finds. It never throws and restores the previous stored key if the new one cannot be applied. Run without a readable key, it wipes only the fallback file and sets `taharah:wipe-pending` in the plain store (after the reset's own wipe of it); the next launch that can read the key ignores the stored one, makes a new key and starts the encrypted file clean, then clears the flag.
- `ZmanimService.getZmanim()` must never throw. It returns `Zmanim | null`, where `null` means the sun neither rises nor sets that day; every caller must handle `null` instead of assuming a value. Depression-angle zmanim that have no solution fall back to their fixed-minute shita (alot 72 min, misheyakir 52 min before sunrise), and misheyakir is always kept inside `(alot, netz)`.
- `scheduleAllImpl()` must isolate each `scheduleOne()` in try/catch so one failing mitzvah cannot empty the whole schedule.
- `skipOn` decisions come from `isSkippedAt()` in [../utils/skipRules.ts](../utils/skipRules.ts), evaluated at the computed window's `start`. Do not add a local copy of that predicate here, and do not judge the skip from `fromDate` — that instant carries the rebuild's clock time.
- `expo-file-system` (read by `SiddurService`) and `expo-keep-awake` (used by the reader) are pinned to the versions already linked into the shipped binary. Raising either is a native change and needs a build.
- `TaskManager.defineTask` calls stay at [NotificationScheduler.ts](NotificationScheduler.ts) module scope, and that module stays imported from the root [../../index.js](../../index.js) entry so both background tasks are defined during headless launches (killed-state `MARK_DONE` taps, background fetch). Route-only imports do not reach headless mode. Pinned by [backgroundTaskEntry.test.ts](__tests__/backgroundTaskEntry.test.ts).

## Work Guidance

- Keep services framework-light and testable; route/component effects should call service APIs rather than duplicate service internals.
- For native-adjacent changes, account for Expo dev-client/native build requirements and web shims.
- When adding ESM or native-adjacent dependencies, check Jest `transformIgnorePatterns` in [../../package.json](../../package.json).
